# UI guide — three tiers, one read layer

There is no single "the UI." There are three ways to look at the same data, all
reading through one seam (`etsy/ui/app_data.py`, D-41), so nothing here can
disagree with anything else — they're not three implementations, they're three
windows onto one query layer.

| Tier | What it is | Needs a server? | Freshness |
|---|---|---|---|
| **Static screens** | Six generated HTML files, one per question | No | As of the last scheduler run (daily, 07:00) |
| **Interactive app** | One page, six tabs, sortable/filterable tables | No | Same — baked in at generation time |
| **Live server** | FastAPI wrapping the same read layer + one live-analysis endpoint | Yes, optional | Live, on every request |

Start with the static screens — they need nothing running and are what the
daily scheduler already produces. Reach for the server only when you want
current-second data or a keyword you haven't watched yet.

---

## Tier 1 — the static screens

Generated by `etsy/ui/home.py` (as a side effect of building the digest) into
`etsy/data/ui/`. Open any of them by double-clicking, or:

```bash
start "etsy/data/ui/index.html"
```

| File | Built by | Answers |
|---|---|---|
| `index.html` | `home.py` | **The front door.** Blockers first (unconfirmed settings, empty vault), then the digest of everything else. Links to every other screen. |
| `calendar.html` (+ `calendar.ics`) | `calendar_page.py` | What to list, and by when — 🔴 now / 🟡 by date / ⚪ watching. The `.ics` file imports into any calendar app so `list_by` dates show up as real reminders. |
| `discover.html` | `discover_page.py` | The ranked candidate pool — terms expanded from your watched seeds, ranked by winnability (demand-per-listing), not volume. Walls are folded into a counted summary line, not hidden. |
| `market.html` | `market_page.py` | The competitor landscape: tracked shops, page-one saturation by dimension, delivery-time distribution. |
| `cockpit-<term>.html` | `cockpit_page.py` | **One candidate, examined.** Three source panels — Pinterest timing, Etsy demand, Etsy competition — kept visually separate, then a combined verdict below them. One file per watched term. |
| `blueprint-<term>.html` | `blueprint_page.py` | The last-mile screen: from "this is winnable" to an actual listing draft — competitor tag mining + demand, refreshed live at generation time (the one static screen with a live step baked into its build, not its viewing). |

**Regenerate on demand** (outside the daily schedule):

```bash
.venv/Scripts/python.exe -m etsy.ui.home
```

This rebuilds `index.html` and, as a side effect, every `market.html`,
`app.html`, and `cockpit-<term>.html` for each currently-watched term.

**Why static-first, not server-first**: these files need no daemon, work
offline, survive a reboot, and are exactly what a non-technical stakeholder
(future you, six months from now) can open with a double-click. The server
tier exists to *add* capability, not to replace this one.

## Tier 2 — the interactive app

One self-contained file, `etsy/data/ui/app.html` (~280KB, no external
dependencies — no CDN script, no network call, works opened from disk).

```bash
start "etsy/data/ui/app.html"
```

Six tabs, all reading from the same embedded JSON snapshot:

| Tab | Shows |
|---|---|
| **Dashboard** | The digest — same top-level view as `index.html`, in-app |
| **Discover** | The full candidate pool, sortable by any column, searchable, filterable by verdict/timing |
| **Etsy** | Keyword demand history with inline sparklines, plus the separate page-one competition table |
| **Pinterest** | Moments (dated, with `list_by`) and featured topics (colour, velocity, momentum) — kept apart, never blended |
| **Calendar** | The same ranked list as `calendar.html`, in-app |
| **Shops** | Tracked competitor shops and their observed deltas |

Every table has the same three controls: click a header to sort, type in the
search box to filter across all visible columns, and a dropdown for the
verdict/timing filters where relevant. Data carrying a non-`measured` basis
(`derived`, `bound`, `default`, `provisional`) is styled distinctly — do not
read a styled-different number as equally solid.

**This file is a snapshot**, generated once per scheduler run, same as the
static screens. It does not update itself; reopening it after the next 07:00
run shows the new data. If you want it live, use Tier 3.

Regenerated by the same command as Tier 1:

```bash
.venv/Scripts/python.exe -m etsy.ui.home
```

## Tier 3 — the live server (optional)

```bash
run_server.cmd
```
or directly:
```bash
.venv/Scripts/python.exe -m etsy.server.app
```

Opens at **http://127.0.0.1:8100/** — the same interactive app as Tier 2, but
rendered fresh from the database on every page load instead of baked in at
generation time. Leave the terminal window open while you use it; `Ctrl+C`
stops it.

| Endpoint | What it adds over Tier 2 |
|---|---|
| `GET /` | The app, live — no waiting for the next 07:00 run |
| `GET /api/docs` | Interactive Swagger UI over every endpoint below |
| `GET /api/{snapshot,meta,keywords,competition,discovered,pinterest,calendar,shops}` | The same data the app reads, as raw JSON, for any other client |
| `GET /api/cockpit/{term}` | One candidate's full verdict, DB-only (no live calls) |
| `POST /api/analyze/{term}` | **The one capability the static tiers cannot have** — runs the real pipeline for a keyword you type that was never watched, live, and stores the result so it joins tomorrow's data too |
| `GET /api/health` | Is the server up, and how many usable sessions does the vault currently have per platform |

**Only `POST /api/analyze/{term}` touches the network.** Everything else is a
thin read over `etsy/ui/app_data.py` — the exact same functions the static
tiers use, so the server cannot drift from the files (D-41). It gates on the
session vault first (`vault_status.scan()`) and returns a clean `503` with a
fix message if the vault is empty, rather than hanging — an empty pool is the
one failure mode this whole codebase is built to never silently swallow.

**Reach it from your phone** on the same network: set `HOST=0.0.0.0` before
starting —

```bash
set HOST=0.0.0.0 && run_server.cmd
```

— but only on a network you trust. **There is no authentication on this
server.** Binding it to `0.0.0.0` puts your private market data (search
volumes, margins, competitor shop deltas) on the LAN for anyone who can guess
the port. See the SaaS/multi-tenancy notes in [`ROADMAP.md`](../ROADMAP.md) for
what would need to change before this is safe to expose beyond a home network.

**Verify it, end to end**, without a browser:

```bash
.venv/Scripts/python.exe -m etsy.server.test_server
```

19 assertions: every read endpoint against a temp DB, filters, the cockpit
route, the empty-vault 503, and the health shape.

## Which tier should I actually use?

- **Checking what to list today** → `index.html` or `calendar.html`. Zero setup.
- **Digging into candidates, sorting, searching** → `app.html`. Zero setup, same data.
- **You typed a keyword nobody's watching yet and want a real answer now** →
  the live server, `POST /api/analyze/{term}`. This is the only tier that can
  do this at all.
- **Wiring an agent (Claude Code / Antigravity) to ask these questions in
  conversation** → neither web tier — see [`docs/MCP.md`](MCP.md).
