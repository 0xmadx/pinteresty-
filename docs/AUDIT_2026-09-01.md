## 3. NEXT.JS UI — possible? Yes. But nothing you need exists yet.

### Minimum path — 5 layers

1. Set `WAL` + `busy_timeout` on both DBs. *(1 hour. Do this regardless of the UI.)*

4. Next.js app, server components fetching that API. *(1–2 days for calendar + keyword table.)*
5. Deploy — currently nothing, since it must run where Redis and SQLite are.

**Rough effort:**
- **Calendar view read-only: ~1 day.** Everything it needs is already in `build_calendar`.
- **Keyword comparison view: harder.** `compare` is a **live private-tier call** with no persistence table and a preflight that silently no-ops if a caller forgets to pass it. A web page that fires it on every load is spending your seller account on page views. You would need to persist results first. **~3 days.**

**My honest opinion on the UI:** build it *only* if you will actually look at a calendar every morning. D-52 deleted the last UI because it was built in two days and never opened again. If the answer is "I ask the agent," then step 1 and step 3 above are still worth doing, and steps 2/4/5 are not.

## 4. SAAS — the honest verdict

**Multi-tenant SaaS on the current architecture is BLOCKED. Not hard. Blocked. Do not start it.**

This is not my opinion; it is what your own code does and what three of your own docs already concluded (`docs/GOAL.md:128-138`, D-31 at `docs/DECISION_LOG.md:450-457`, `ROADMAP.md:100-135`).

**The reason, in one sentence:** the private tier has no application-level identity — **the request IS the seller**.

Every valuable private call is Etsy's internal seller-dashboard AJAX (`etsy/api/private/api.py:403, 445, 492, 550, 619`), all with `/shop/{shop_id}/marketplace-insights/...` in the path. `core/session_manager.py:143-156` formats the leased account's `shop_id` into that URL, injects its `csrf_token` as `x-csrf-token`, and injects its harvested browser cookies. There is no Etsy OAuth client anywhere in this repo — I checked; the only matches are vendored `.venv` packages. **There is no "act on behalf of" parameter to add.**

So multi-tenancy means: each customer installs your Chrome extension, stays logged in to Etsy, and their **live seller login sits in your Redis** while you scrape Etsy as them, through a Chrome-124 TLS impersonation layer (`core/session_manager.py:65-67`, comment: *"to pass TLS fingerprinting checks (Akamai/DataDome)"*). **One ban is a customer's business, not a re-login.**

**Five things the code makes worse than the docs admit:**

1. **The vault randomises across the whole pool.** `core/cookie_vault.py:196` — `get_valid_account(platform)` takes **only** the platform. `:215-216` shuffles every candidate. There is no `profile_id` argument, no filter, no affinity anywhere in the repo. Add a second tenant and tenant A's question goes out as tenant B's shop. **Cross-tenant impersonation is the default path, not an edge case.** And the lease is released after *every* request (`session_manager.py:106-108`), so identity re-rotates per request.
2. **The cheap fix is closed.** Namespacing the platform string breaks silently: `session_manager.py:143` tests `platform == "etsy_private"` by exact equality (csrf/shop_id would stop injecting) while `:132` uses `"etsy" in platform` (cookies still apply). A real fix means editing the Rule-6 access layer.
3. **429 evicts (see C1).** N tenants behind one egress IP generate 429s constantly. Each one hard-removes a seller session.
4. **Zero tenant columns.** 18 tables, plus the cache — grep returns two unrelated comments. Worse, the primary keys are natural business keys (`keyword`, `listing_id`, `shop_name`, `term_id`, `trend_name`), so partitioning rewrites every PK, every INSERT and every SELECT, across ~33 no-arg DB constructions and 4 modules with module-level `DB_PATH` constants. And paths are inconsistent: `settings.json`, `graph.db` and `request_cache.db` follow cwd, but `market_intelligence.db` resolves off `__file__` (`core/database.py:11-13`) — so the "one cwd per tenant" hack gives separate config and **a shared main database**.
5. **The cache is flat-keyed** on query alone (`results_data_{query}`), so tenant B is served payloads tenant A's seller session paid for. There is no per-tenant rate limit, quota or metering anywhere. And no concurrency: no WAL, no `busy_timeout`, no threads — two tenants writing means *"database is locked"*.

**On legal:** I am not a lawyer and I will not give a verdict. The factual posture: a repo-wide grep for `terms of service | robots.txt | GDPR | data protection | LICENSE` returns **zero hits**. There is no LICENSE file. Meanwhile the code forges a browser TLS fingerprint to defeat bot detection, detects DataDome markers and rotates identity, and replays harvested login cookies. Doing that to **your own** account is one thing. Doing it **for paying customers whose credentials you hold** is a materially different position. If you ever go there, get advice first — do not get it after six months of building.

### What IS sellable

Your own `GOAL.md:138` already says it: **"the analysis engine is sellable and the access layer is not."**

The realistic product is **public tier + the judgement layer** — 53–55 offline suites, ~1,500 assertions, no network, no login. That works for anyone. It gives up search volume, `query_cvr`, the seasonal curve and trending terms — roughly half of what makes this better than a niche checker. That is the honest trade.

The other honest option: **sell the judgement, not the data.** The customer brings their own numbers; your product supplies the profit gate, the calendar, the wall check, the refusals. That travels, and needs no credentials at all.
