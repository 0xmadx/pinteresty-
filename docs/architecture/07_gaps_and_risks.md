#### 🟠 S-1b · The root cause: Etsy stores a rotating token where Pinterest stores a secret-free file

The two halves take opposite approaches to the same problem, and only one is safe.

> **Status change, 2026-08-11.** The two servers were merged into one
> `core/cookie_server.py` with a `platform` router — which correctly resolves the
> duplicate logged at §F-12. **But the consolidation went toward `.env`, not away
> from it.** Pinterest now writes `PINTEREST_COOKIES` into `.env`
> (`core/cookie_server.py`), `pinterest/core/client.py` reads it from there, and
> `pinterest_cookies.json` was deleted. The safe path was removed and the unsafe one
> extended. The table below is kept as the record of what the two approaches were,
> and why the deleted one was the right model.

| | **Etsy** | **Pinterest — *before* 2026-08-11** |
|---|---|---|
| Destination | `.env` — `dotenv.set_key` in `core/cookie_server.py` | `pinterest_cookies.json` (now **deleted**) |
| Git status | ❌ **tracked** | ✅ **never tracked** (`.gitignore:7`) |
| Co-located with | `CAPSOLVER_API_KEY`, `DEEPSEEK_API_KEY` — long-lived secrets | nothing else |
| Rotation cadence | every ~4 min (extension refresh) | every ~4 min |
| Net effect | every rotation dirties a **tracked** file that also holds two API keys | rotation touched an ignored file only |

**Both platforms now land in the tracked file.** The exposure roughly doubled: a
second live session credential joined the three that were already there.

**This is why S-1 happened.** A token rewritten every four minutes into a tracked
file produces a constant stream of `.env` diffs — which trains you to stop reading
them, and that is how two long-lived API keys got committed without anyone noticing.
The Pinterest side never had this problem because the rotating value never shared a
file with a secret.

**The fix is already half-provisioned.** `etsy_datadome.txt` exists at repo root
(128 bytes) and is **already gitignored** (`.gitignore:8`) — but **nothing reads or
writes it**. The destination is sitting there unused.

Point the DataDome relay at it, and leave `.env` for long-lived secrets only:

| File | Line | Change |
|---|---|---|
| `core/cookie_server.py` | `:27-36` | write to `etsy_datadome.txt` instead of `dotenv.set_key(.env, …)` |
| `core/settings.py` | `:29` | read `DATADOME_COOKIE` from that file, falling back to env |
| `core/session_manager.py` | `:40,54` | same read path |
| `etsy/api/public/api.py` | `:21-22` | **no change** — it reads via `self.config`, so keeping the attribute name makes this transparent |

⚠️ **Not implemented by this pass.** All four files are session-handling code, which
`PROJECT_BRIEF.md:51-63` and the `system-architect` skill place off-limits to
modification. This is recorded as a recommendation for the operator to make.

The recommendation is **secrets hygiene, not an access-layer improvement** — it makes
the system no better at reaching Etsy, only worse at leaking credentials. It also
makes `.env` stable enough to publish as `.env.example`, which closes S-1 properly
rather than just untracking the file and waiting for it to be re-added.

### ✅ B-4 · Negative reviews are systematically under-sampled — **fixed 2026-08-11**

Was the compounding of two defects: `reviews_api.py` set `rating = 5` as the
**default**, overridden only on a string match against the immediate parent; and
`sentiment_analytics.py` filtered `rating <= 3` on those fabricated values. Every
review whose markup didn't match became a 5-star review, so a listing with real
complaints could report `"No critical reviews found to analyze."` — the AI flaw
analysis was biased toward "customers are happy" by construction.

**What changed.** A rating is now **measured or `None`, never fabricated**: the parse
(extracted to a pure `parse_reviews_html()` for offline testing) walks up to three
ancestors for the `"N out of 5 stars"` text and tags each review
`rating_basis: measured | unparsed`. `sentiment_analytics.py` excludes unrated reviews
from **both** buckets, reports an `unrated_count`, and when the parse fails on every
review it says so explicitly — "0 critical" now means *unmeasured*, not flawless.
Guard test: `etsy/api/public/test_reviews_parse.py`, 10 assertions, no network.

Still open: `"date": "Recent"` is hardcoded where a date belongs.

## T — Temporal (invariant 2)

### ✅ M-3 · The LEARN loop had no input — **closed 2026-08-11**

Nothing recorded what was actually listed, so D-12's calibration rule ("no auto-tuning
below 10 launches") had nothing to count and every week of outcomes was unrecoverable.

The operator added `launches` and `rank_observations` to `core/graph_db.py` with
`record_launch()` / `record_rank()`. This pass added the halves that had no callers:

| Piece | What it does |
|---|---|
| `etsy/analytics/launch.py` | CLI. Ties a real `listing_id` to the prediction snapshot `listing_generator` wrote at generation time. |
| `listing_generator.py` | Now writes `<seed>.prediction.json` beside the brief — volume, supply, gap/SERP scores **as they were when the decision was made**. |
| `etsy/analytics/rank_tracker.py` | Reads every launch, searches the public SERP for its term, records where it landed. Reuses `get_public_search` — no new access-layer code. |
| `prediction_vs_outcome()` | The join the loop exists for: did what we predicted would do well actually rank? |

**Why the prediction is snapshotted rather than recomputed.** Volume, supply and SERP
strength all move. A "prediction" reconstructed after the outcome is known is not a
prediction — scoring the model against it would flatter it silently. The launch itself
happens outside the system (the operator lists on Etsy; only then does an id exist), so
the snapshot waits on disk until `launch.py` attaches an id to it.

**Three states, kept distinct.** This is the whole point of the table shape:

| State | How it is stored |
|---|---|
| ranked | a row with `rank` (and `absolute_rank`) set |
| checked, not in results | a row with `rank = NULL` — **a measurement** |
| never checked (the search itself failed) | **no row at all** |

The tracker deliberately writes nothing when the search fails: recording `rank=NULL`
there would assert "not in the results", which was not observed. `observations` in the
join distinguishes the last two.

**A gap this pass found in its own work.** The first version recorded one `rank` column
while the module docstring — and `MIGRATION_AND_OPERATIONS.md:111` — required *both*
organic and absolute. It was storing organic and discarding absolute, visible only in a
test's console output (`organic=1 absolute=2`). A listing can slide in absolute rank
while holding organic rank purely because a competitor started buying ads; one number
makes that look like a ranking loss it is not. `absolute_rank` added while both tables
were still empty. 34 offline assertions in `etsy/analytics/test_rank_tracker.py`.

⚠️ **Still needs a schedule.** `MIGRATION_AND_OPERATIONS.md:111` wants this 3×/week.
Nothing runs it automatically — `python -m etsy.analytics.rank_tracker` is manual until
it is put on a timer.

### ✅ O-1 · The run was unobservable — **structured run log added 2026-08-11**

`MIGRATION_AND_OPERATIONS.md:118` — *"a weekly batch system fails silently"* — and none
of its five health questions could be answered. The repo had ~330 `print()` calls across
30 modules.

**The prints were not the defect.** Converting each one to `logger.info()` would have
answered exactly zero of the five questions, because the missing thing is a *per-stage
record with counts*, not better-formatted lines. So `core/runlog.py` adds the record and
leaves the console output alone — an operator watching a run still gets readable text.

```python
with stage("discover", seed=seed) as s:
    ...
    s.count(rows_out=42, cache_hits=10, metered_calls=2)
```

One JSON line per stage appended to `etsy/data/logs/run_<date>.jsonl`, carrying stage,
duration, the six counters, guard-flag counts, notes and caller context — exactly the
fields `MIGRATION_AND_OPERATIONS.md:132-134` specifies.

| Health question | Answered by |
|---|---|
| 1. Did every stage complete? | `health()["stages"]` / `failed_stages` |
| 2. How fresh is the freshest data? | `MAX(collected_at)` per observation table |
| 3. How many rows were guard-flagged? | auto-captured from `core/guards.py` per stage |
| 4. What did the budget cost? | `metered_calls`, cache hit rate |
| 5. Did any circuit breaker trip? | **`None` — reported as unimplemented** |

Question 5 deliberately returns `None`, not "none tripped". No breaker exists, and an
all-clear from a detector that does not exist is precisely the plausible-wrong-answer
failure this system is built to avoid.

Two decisions worth recording:
* **A crashed stage still crashes.** The record is written, then the exception re-raised
  — `MIGRATION_AND_OPERATIONS.md:146` says re-run it, everything is idempotent and
  cached, so swallowing it would trade a loud recoverable failure for a quiet partial one.
* **Unknown counter names raise.** A typo'd counter would otherwise vanish and quietly
  under-report the budget.

Run `python -m core.runlog` for the report. Storage is a JSONL file and nothing more — at
single-operator weekly-batch scale that is the whole requirement. 40 offline assertions
in `core/test_runlog.py`.

**All 15 operator entry points are instrumented**, via a `@logged_stage("name")`
decorator so a 200-line `run()` did not have to be re-indented to gain a record:

| Stage | Module |
|---|---|
| `discover`, `arbitrage` | `master_arbitrage.py` (explicit `with stage(...)`) |
| `niche_finder` | `master_niche_finder.py` |
| `grid_analytics` | `grid_analytics.py` — counts rows in/out/errors |
| `sentiment_analytics` | `sentiment_analytics.py` — counts unrated reviews as errors |
| `single_listing_analytics`, `seo_analytics`, `shop_analytics` | `etsy/analytics/` |
| `master_listing_analyzer`, `private_blueprint`, `private_comparison`, `private_recursive_spider` | `etsy/engines/` |
| `daily_tracker`, `ratio_estimator` | `etsy/analytics/` |
| `ssr_graph_bfs` | `ssr_graph_pipeline.py` |
| `listing_generator` | `listing_generator.py` (`__main__` sequence) |

`runlog.count(...)` reaches the running stage through a `ContextVar`, so code deep in a
pipeline contributes row counts without every function between growing a parameter. It
is a **no-op outside a stage** on purpose — these modules are also imported by tests and
run ad hoc, and instrumentation you have to work around gets removed.

Only `private_scoring_pipeline.py` is uninstrumented: it still cannot import
(`src.services.executor`, §B-2), so there is no stage to record.

**A nesting bug this surfaced.** `master_arbitrage`'s `discover` stage wraps
`master_niche_finder.run()`, which is itself a stage — so guard failures inside the child
were counted *again* by the parent, and `health()` double-reported them. Found by running
the nested case, not by reading the code. Stages now clear the guard collector on **exit**
as well as entry, so each failure is attributed to exactly one stage; a parent still
records anything failing before its child starts or after it ends. Pinned by four
assertions.

### ✅ T-2 · Nothing in the pipeline could say "no" — **profit gate wired 2026-08-11**

`profit.py` existed but nothing called it, so every engine still ranked purely on demand
and supply. `GOAL.md:104-120` is explicit that this is what made the original design pick
the wrong products.

**`master_niche_finder.py` STEP 5** is now the first step in the system that can reject a
candidate:

| Piece | Behaviour |
|---|---|
| `product_profile` ctor arg | What the operator would actually make. A keyword has no COGS or build time; a *product* does. Defaults to a digital download — the only type whose economics follow from price alone. |
| Price input | The **low** end of the measured median band. Clearing there means clearing across it; using the high end would flatter every candidate. |
| `parse_price()` | Measured or `None`. `private_blueprint.py:95` coerced `"Unknown"` to **0.0**, which reads as a catastrophic loss rather than as missing data. |
| No price → `unjudged` | Carried through separately, **never rejected**. Dropping it would be indistinguishable from judging it unprofitable. |
| Gate, not a weighted term | D-01. Below-floor is not "a lower score", it is not worth listing. |
| Rejects are kept | With verdict and reasons, in `rejected_on_profit`. Nothing silently disappears. |

`master_arbitrage.py` then arbitrages **only** what cleared the gate — slicing an
unprofitable keyword seven ways costs ~20 public requests and cannot change the verdict.
`top_3_deep_dive` keeps its old meaning so existing consumers are unaffected.

Guard test `etsy/analytics/test_profit_gate.py`, 29 assertions. One worth noting: the
70% digital floor bites at **~$2.20**, not where intuition puts it — margin is
`0.905 − 0.45/price`, so the fixed $0.45 (listing + processing flat) is what kills cheap
downloads, not the percentage fees.

⚠️ `demand_units_per_week` stays an **operator input**. The private API returns CVR as an
ordinal bucket (1-4), not a rate, so converting search volume into weekly units would be
fabrication. Without it the margin gate is fully live; `weekly_profit` and the capacity

### 🟠 T-3 · Time-varying Pinterest series are cached under a **dateless key** — found 2026-08-11

Surfaced the moment B-4b was fixed and `pinterest/tests/test_local_derivations.py` could
run for the first time. It fails 2 of 17:

```
[FAIL] related_terms counts[] is byte-identical to /metrics/?days=365   0/5 matched
[FAIL] prefix_match counts[] == metrics[1:] within 2 units             max deviation 82
```

**Not a flaky test — a cache-key defect.** Compare how the three keys are built in
`pinterest/endpoints/api.py`:

| Endpoint | Line | Key includes the date? |
|---|---|---|
| `metrics` | `:237` | ✅ `metrics_{end_date}_{days}_...` |
| `related_terms` | `:269` | ❌ `related_{country}_{term}` |
| `prefix_match` | `:285` | ❌ `prefix_{country}_{query}` |

All three return a **weekly time series**. Only `metrics` is keyed by the week it
describes, so a `related_terms` response harvested weeks ago is served forever under the
same key — and `SeriesStore` then hands that stale curve to `pin_graph_pipeline` as
